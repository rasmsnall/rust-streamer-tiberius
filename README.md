# tiberiusdelta

Stream a live **Microsoft SQL Server** database into **Delta Lake** tables,
**incrementally**. Rust core, Python bindings, intended for use from Databricks.

Each run pulls only the rows new or changed since that table's own last successful run,
and merges them into a Delta table keyed on its primary key. A table of fifty million rows
with a thousand daily changes transfers a thousand rows.

```
SQL Server -> SELECT ... WHERE watermark > checkpoint -> Arrow -> Delta MERGE
```

Sibling project to [`rust-streamer-pgdb`](https://github.com/rasmsnall/rust-streamer-pgdb)
(pgdelta), which does the same job for delivered `pg_dump` files. Three assumptions are
flipped here: a live connection instead of a file, credentials that matter, and
incremental sync instead of a full reload.

## Install

```bash
pip install tiberiusdelta-0.1.0-cp310-abi3-manylinux_2_28_x86_64.whl
```

One `abi3` wheel loads on CPython 3.10 and later. **Nothing else to install**: no ODBC
driver manager, no driver binary, no C toolchain. Connectivity is
[`tiberius`](https://docs.rs/tiberius), a pure-Rust TDS client that speaks SQL Server's
own wire protocol over a plain socket.

## Use

```python
import os
import tiberiusdelta

TABLES = [
    {"table": "dbo.customers", "watermark_column": "updated_at", "primary_key": "id"},
    {"table": "dbo.invoices", "watermark_column": "modified", "primary_key": "invoice_id"},
]

report = tiberiusdelta.sync_tables(
    os.environ["SQLSERVER_CONNECTION_STRING"],
    "/Volumes/main/raw/mssql/",
    TABLES,
)

for t in report.tables:
    print(t.table, t.rows_fetched, t.rows_inserted, t.rows_updated)
```

Check the configuration against the live source first, without writing anything:

```python
for t in tiberiusdelta.preflight(connection_string, TABLES):
    print(t.table, "ready" if t.ready else "NOT READY")
```

## How it works

For each configured table, in this order and never the reverse:

```
read checkpoint -> SELECT rows above it -> MERGE into Delta (commits) -> advance checkpoint
```

Advancing the checkpoint last is what makes a crash safe. The next run re-fetches rows
that may already have been applied, and because the merge is an upsert, re-applying them
updates in place rather than duplicating. Checkpoint-first would permanently skip rows that
were never merged.

Checkpoints live in a `_streamer_checkpoints` Delta table beneath the output prefix, one
row per source table.

## What it will not do

Stated up front, because each of these is silent rather than loud:

- **Deletions are not detected.** A row deleted at the source stops appearing in the query
  result, which is indistinguishable from it not having changed. Its copy in Delta remains.
  Detecting deletions needs a soft-delete column at the source, or CDC.
- **A tie on the watermark loses the row permanently.** The filter is strictly
  greater-than. Choose a watermark column precise enough, or strictly monotonic enough,
  that genuine ties cannot occur.
- **Correctness depends on the watermark column never decreasing**, which this library
  cannot verify.
- **No cross-table consistency.** Each table is queried independently, at a different
  moment. The atomic unit is one table's merge.
- **Tables are never discovered.** A table not in your configuration is not synced.

## Requirements

- A **`SELECT`-only** database account. The library issues only `SELECT`, but TDS has no
  client-side read-only mode, so the grant is where that guarantee actually lives.
- A TCP route from the compute to the instance, and `Encrypt=true`.
- An **index on each watermark column**, or every run is a full scan and a sort.
- Output to an external location or a `/Volumes/...` path, never a Unity Catalog *managed*
  table.
- A scheduled `VACUUM`. Merges rewrite files; the superseded ones stay until vacuumed.

## Development

```bash
cargo test --lib --doc                 # unit tests and doctests, no database needed
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

The end-to-end tests need a SQL Server. One throwaway container, and the fixtures the
tests expect:

```bash
docker run -d --name tiberiusdelta-test-mssql -p 14330:1433 \
  -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD='Test_Passw0rd!2026' \
  mcr.microsoft.com/mssql/server:2022-latest

export MSSQL_SA_PASSWORD='Test_Passw0rd!2026'
python tools/seed.py
cargo test --test mssql_live
```

`.devtest/type_zoo.sql` seeds one nullable column of every mapped type, with one row of
values and one of NULLs. It exists because what a given T-SQL type actually decodes to is
a property of TDS and tiberius rather than of this code, so only a real server can prove
the mapping. It earned its keep immediately, catching two real defects on its first run.

`tools/smoke.py` runs the same round trip through the built wheel, which is what CI does
after building it.

## Status

Implemented and verified end to end against SQL Server 2022, across every type it maps,
through both surfaces. **Not yet run against a production source**; see
